# UX: повторный «Показать ещё» и поздний ответ могут смешать страницы списка

## Summary

В App.list.more нет busy/token защиты: два вызова могут запросить один offset и добавить обе порции, а ответ more может дополнить уже обновлённый другим поиском loaded. Refresh защищён ticket, но more — нет. Исследование n22/n55; src/titanium_platform/ui/list.js. Нужен сценарий с управляемыми задержками, без предположения о реальной частоте сбоя.

## Steps to reproduce

1. Открыть серверный App.list с минимум 45 тестовыми записями и задержать ответ следующей порции.
2. Быстро дважды нажать «Показать ещё», до завершения первого запроса.
3. В отдельном повторе запустить загрузку порции, затем изменить поиск или фильтр и вернуть старый ответ позже нового.
4. Сымитировать ошибку следующей порции и проверить возможность локального повтора.

## Expected

Одна порция загружается один раз; повторное действие заблокировано или объединено. Поздний ответ старого запроса не смешивается с новым поиском. Ошибка сохраняет уже видимые строки и предлагает повтор.

## Actual

more напрямую ждёт remote(loaded.items.length,page), потом дописывает next.items к текущему loaded. Нет проверки актуальности, busy состояния и локального обработчика ошибки; вывод следует из кода, runtime-воспроизведение ещё не записано.

## Environment

Исходное дерево 3716444 / версия приложения 0.38.0, статическая сверка 2026-11-05. Браузер/Electron и вспомогательные технологии в этой задаче не запускались. Использовать тестовую мастерскую; данные оператора не изменять. P0 — порядок работ по research, severity medium — отдельная оценка дефекта.

Проверка не требует реального удаления или изменения рабочей мастерской.

## Acceptance criteria

- [ ] Два быстрых клика не создают повторных строк и не пропускают записи.
- [ ] Задержанный ответ прежнего фильтра/поиска не меняет новый список.
- [ ] Ошибка даёт локальный повтор без потери строк и состояния; счётчик показано N из M верен.
