## Context

Для перехода от предложения к реализации нужны конкретные зависимости DEV/REQ, проверяемые промежуточные результаты и непротиворечивое назначение версий публикации.

## Alternatives

1. Реализовывать всю фичу без промежуточных результатов.
2. Начать облако до доказанного числового переноса.

## Decision

Применить матрицу DEV-01…DEV-11 и контрольные точки G0…G4. Формирование неизменяемого онлайн-выпуска выполняется после резервирования серверных идентификаторов; исходное происхождение отделено от облачного владения.

## Reason

Каждая работа получает явный контракт, способ проверки и условия перехода к следующему этапу.

## Границы инкрементов

- G0/D0: подтверждены нативные зависимости и числовые данные без исходников; если проба неуспешна, обновить оценки, не объявлять платформу поддержанной.
- G1/D1–D2: две независимые мастерские обмениваются файлом, получают одинаковые числовые результаты; этот выпуск полезен без сервера.
- G2/D3: чистая машина устанавливает приложение, открывает старую мастерскую и работает офлайн; публиковать подписанный релиз можно только после D6.
- G3/D4–D5: целый выпуск доступен онлайн при выключенном компьютере автора; другой аккаунт не может изменить его; нет фотографий в HTTP-передаче.
- G4/D6: выполнены REQ-078, восстановление и матрица распространения; вопросы Q-001, Q-002, Q-003, Q-009 закрыты для соответствующего объёма беты.

## Уточнение подготовки онлайн-выпуска

Чтобы назначенный сервером номер не изменил уже вычисленный хеш, POST publication сначала резервирует release_id и release_number. Клиент формирует окончательный manifest с этими значениями, затем канонизирует, вычисляет хеш и отправляет чанки. Finalize публикует только этот неизменный контент. Пропуски зарезервированных номеров после отмены допустимы; порядок успешных выпусков монотонен. expected_previous_release_id защищает от конкурирующей публикации. Файловый неопубликованный экспорт не имеет серверного номера; его публикация готовит отдельный серверный выпуск со стабильными исходными measurement_id и engraving_id, а не меняет импортированный файл на месте.

## Уточнение источников идентичности

origin_lab_id стабилен для исходной локальной лаборатории; cloud lab_id идентифицирует облачное пространство владельца. Первая публикация связывает их на сервере; API не позволяет второму аккаунту присвоить уже связанное происхождение. Если допускаются несколько облачных представлений одного исходного набора, это отдельная явно проверяемая связь, а не переназначение происхождения. server_owner — утверждение сервера о праве публикации, а не независимое доказательство физических измерений автора. Файл со свободно введённым автором не получает серверную метку подтверждения без проверки выпуска и хеша.

До DEV-06 явно оформить обновление основной фичи titanium-color-engraving-intelligence-platform: REQ-043 и DEC-020 сохраняют локальную работу и LightBurn, но формулировка одного процесса уточняется до одного пользовательского приложения с управляемым backend. ## Проверки и ограничения работ

Контрактные тесты выполняются на synthetic fixtures и тестовой копии мастерской. Рабочая база оператора не изменяется ради проверок. Исходные неизменяемые наблюдения сохраняются. Проверка приватности сравнивает реальные байты файла и HTTP-тела. Код, найденный в импортируемой структуре, не выполняется. Сетевые тесты используют два аккаунта с независимыми правами. Локальная регрессия запускается по действующим правилам проекта; отключённый CI не включается автоматически. Покупки, получение сертификатов и облачное развёртывание не входят в создание документации.
