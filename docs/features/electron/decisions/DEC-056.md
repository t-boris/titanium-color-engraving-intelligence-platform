## Context

REQ-081 asks that an upgrade never leaves the workshop half-migrated, that a newer schema is refused with an explanation, that two processes cannot open one workshop, and that the operator can make a full backup and restore it into another folder or, explicitly, over the current one, with stored absolute paths surviving a move. Before this the Store ran CREATE TABLE IF NOT EXISTS and ad-hoc ALTER TABLE at every start with no stamp, no copy and no lock.

## Alternatives

1. Keep the additive start-up migration without a stamp: a downgrade or an interrupted change is invisible and cannot be explained or undone.
2. A full workshop backup (files and photographs too) before every migration: minutes and gigabytes for a schema change of seconds; the database copy is what a rollback needs, the files are untouched by migrations.
3. Store relative paths only, rewriting every reader: a larger change for the same result; one resolver that rebases the recorded root is enough and new rows may stay as they are.
4. Refuse to restore over the current workshop at all: the operator then copies folders by hand, which loses the hash check and the set-aside copy.

## Decision

migrations.py keeps the schema version in PRAGMA user_version (CURRENT = 1 for the schema of 0.29.0); every later change is an entry of its registry and runs in one BEGIN IMMEDIATE transaction together with the new stamp, so the workshop is either at the old or at the new version. Before any registered migration the Store checks free space (twice the database plus its WAL plus 64 MiB), writes a recovery copy backups/schema-before-<CURRENT>-<UTC>.sqlite with SQLite's backup API and verifies it with integrity_check; a failed copy stops the migration. A workshop whose stamp is above what the application knows is refused with SchemaTooNewError naming both versions and the recovery copy to roll back to. Opening a workshop takes workshop.lock (flock, msvcrt on Windows) and a second process is refused with WorkshopLockedError; closing releases it. Rollback is: stop the application, put the recovery copy in place of titanium.sqlite (or restore a full backup), start the previous version. backup.py makes a full backup (database snapshot, files/, labs/ without .staging, lab_exports/, fonts/) with a manifest of hashes written last, so an incomplete backup is never mistaken for a complete one; inspect verifies the hashes; restore goes into another folder by default and over the current workshop only when the request says overwrite:true and confirm:"overwrite", in which case the current workshop is set aside as <name>.replaced-<UTC> rather than deleted. files.rebase_all rewrites the stored absolute paths (pairs, device documents, plan data) from the recorded root to the new data folder and the setting restored_from records the move. The operator's live workshop is stamped on its first start after the deploy, which is always preceded by the deploy's own database backup.

## Reason

Atomic migrations with a verified copy make an upgrade reversible without asking the operator to understand SQLite; the stamp makes a downgrade explainable instead of silently corrupting; the lock prevents the one failure mode SQLite does not protect against across two application instances; the manifest-last backup and the set-aside restore keep both the old and the new workshop until the operator decides.

## Consequences

Every schema change from now on is a registry entry with a stamp, never a bare executescript; tests/test_migrations.py and tests/test_backup.py cover the copy, the refusal, the lock, the manifest and the rebase; the workshop screen (REQ-081) shows backups, recovery copies and the restore choice; the deploy procedure keeps its own backup before the first start of a new version.
