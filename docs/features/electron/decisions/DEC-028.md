## Context

Публикуются сравнительно небольшие числовые наборы; обычное приложение не должно содержать общий пароль к БД.

## Alternatives

1. Соединять desktop напрямую с Neon административной ролью.
2. Выделять отдельную БД каждой лаборатории.
3. Перенести Python/RAW на сервер и добавить S3 для всех исходников.

## Decision

Предлагается HTTPS API и каталог на Vercel, одна PostgreSQL-база Neon с логическим владением лабораториями. Только сервер имеет доступ к БД. Снимки неизменяемы и доступны после атомарной публикации. S3 для исходных пользовательских данных не требуется.

## Reason

Уменьшает инфраструктуру и отделяет права публикации от привилегий базы данных.

## Consequences

## Облачная модель и API — предложение

Логические сущности: accounts, labs(owner_account_id), releases(immutable manifest + content chunks), release_items/индексы каталога, revocations, publication_uploads и audit. Пользователь создаёт несколько лабораторий в одной физической БД; separate database per lab не требуется. Публичное чтение не требует регистрации; создание и изменение публикаций требует входа владельца. Закрытые лаборатории, редакторы и модерация вкладов — следующий этап после отдельного решения о доступе.

Предлагаемые ресурсы: GET /labs, GET /labs/:id, GET /labs/:id/releases, GET /releases/:id/manifest, GET /releases/:id/chunks/:n; POST /labs, POST /labs/:id/publications, PUT /publications/:id/chunks/:n, POST /publications/:id/finalize, POST /releases/:id/withdraw. Все мутации проверяют владельца. Идемпотентный ключ привязан к аккаунту и операции; finalize проверяет полный хеш и expected_previous_release_id, фиксирует целый выпуск и индекс каталога одной транзакцией. Незавершённая загрузка не видна читателям.

При размещении API в Functions нельзя пересылать 16 MiB одним обычным запросом. Предложение: чанки не более 1 MiB с ограниченным числом записей и серверной сборкой/проверкой; скачивание тоже чанками. Предельные размеры проверять в текущей документации платформы перед реализацией. Крупные наборы в будущем могут перейти в объектное хранилище без изменения модели выпусков.

Данные загрузки имеют срок жизни; повтор запроса использует тот же upload_id. Локальные подписки хранятся локально, пока не появилась отдельная потребность в синхронизации аккаунта. Сервер не получает информацию об изображениях и проектах подписчика.



RLS — дополнительная защита при использовании непривилегированной runtime-роли; API проверяет владельца независимо от RLS. Административная/owner/BYPASSRLS-роль не применяется для пользовательских запросов. Экспорт/восстановление облачной БД проверяется отдельно; логирование не содержит полных наборов и токенов. Конкретные тарифы и стоимость оцениваются после измерения размеров и нагрузки, цены здесь не фиксируются.
