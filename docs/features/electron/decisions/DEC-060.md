## Context

DEC-058 described the sign-in as a handoff: the cloud's page signs the operator in with Neon Auth from the browser and leaves the session token with the cloud under a one-time code, and the core turns the session token into JWTs at Neon Auth's GET /token. Built and probed against the real Neon Auth on 2026-10-24: only the signed cookie value (token.HMAC, signed with Neon's secret, HttpOnly) authenticates at /token and /get-session; the bare session token of the sign-in response answers 401 or null, as a Bearer header does. No page can read that cookie for the core, and Neon Auth offers no bearer, device-code, API-key or one-time-token plugin (OpenAPI: 79 routes; supported plugins Admin, Email OTP, JWT, Magic Link, OAuth Provider, Organization, Open API, Phone Number). Its documentation names the OAuth provider as the way for a desktop app or CLI: the authorization code flow with PKCE against a managed public client, access tokens as EdDSA JWTs for a named resource (an hour), refresh tokens of thirty days rotated on every use, with the login and consent pages hosted by the application's own service. REQ-086 asks for sign-in through the managed provider without a password form of the core's own and with the token outside the workshop's data; the plan said the result returns to a loopback callback with state and PKCE. Evidence: docs/features/electron/cloud-signin-2026-10-24.md.

## Decision

Neon Auth's OAuth provider is enabled on the branch (Console API, 2026-10-24): login page https://titanium-labs-api.vercel.app/signin, consent page https://titanium-labs-api.vercel.app/consent, protected resource https://titanium-labs-api.vercel.app; one managed public client «Titanium Workshop» (client id uuftXbnCKvixZxlXIknNvggUDzZtlmHT, not a secret, served by GET /auth/config) with the single redirect URI https://titanium-labs-api.vercel.app/auth/return and consent not skipped. The core (both run modes, cloud_session.py) reads GET /auth/config (Neon Auth's address, client id, resource, redirect address, providers) and Neon Auth's discovery document (whose issuer must equal the address the cloud named), makes a state of the form random.port where port is the loopback port the browser reaches the core on, and a PKCE verifier, and opens the authorization endpoint in the system browser with scope openid profile email offline_access and the resource. The cloud hosts the login page (signin.html: e-mail and password, a new account, or a social provider, passing Neon Auth's signed request back as oauth_query; a signed-in browser continues through POST /oauth2/continue) and the consent page (consent.html: client name from GET /oauth2/public-client, the scopes, the resource and the return host; POST /oauth2/consent). Neon Auth returns the browser to GET /auth/return, which answers 302 to http://127.0.0.1:port/api/cloud/callback with the state and the code (or the error), and to nothing else; a malformed state is 400. The core's guard lets that callback through without the desktop session cookie only while the state is pending. The core exchanges the code and its verifier at the token endpoint (client_id in the form body, redirect_uri, resource) for an access token and a refresh token, asks the userinfo endpoint for sub, name and e-mail, and keeps the refresh token with the endpoints in data/cloud/session.json (mode 0600); access tokens live in memory and are renewed a minute before they expire; refreshes are serialised and the rotated refresh token is written before use, because a refresh token presented twice revokes the whole sign-in at Neon Auth; a refresh answered invalid_grant or 401 ends the sign-in here with an audit entry; sign-out revokes the refresh token (best effort) and deletes the file. The cloud verifies two kinds of JWT against the JWKS: the desktop's OAuth access tokens (iss the Neon Auth base URL, aud containing the service's address) and the JWT plugin's tokens of a browser session (iss and aud the Neon Auth host, used by the live tests and the smoke), so NEON_AUTH_ISSUER and NEON_AUTH_AUDIENCE are comma-separated lists; the account id is the subject either way. The handoff endpoints and the auth_handoff table are gone (migration 0003); the service keeps nothing of a sign-in. This replaces the sign-in paragraph of DEC-058; the rest of DEC-058 stands.

## Reason

The sign-in handoff of DEC-058 cannot work against the real Neon Auth: only its HttpOnly signed cookie authenticates /token, and no page can read it for the core. Neon Auth's OAuth provider is its documented way for a desktop application or CLI; it was enabled, built and verified end to end against production on 2026-10-24.

## Consequences

The sign-in works with the real provider: scripted end to end against production (docs/features/electron/cloud-signin-2026-10-24.md) and through the real core (sign-in, a verified call, a forced refresh with rotation, sign-out). The operator approves the application once per account on the consent page (remembered by Neon Auth); Google sign-in goes through the same login page. A workshop stays signed in while it is used at least once a month (the refresh token's life, renewed on use); after that, or after a sign-out elsewhere, the core asks to sign in again. The authorization code passes through the browser's address bar and the cloud's return redirect, as in every web OAuth flow; it is single-use and useless without the core's verifier. The core keeps a refresh token on disk under the workshop's own file permissions (as the LAN keys), not in Electron safeStorage: the same file serves both run modes, and the console application has no safeStorage. The Neon configuration (provider, client) is part of the deployment, documented in cloud/README.md; a second environment needs its own client and pages. Risks: Neon's OAuth provider is marked beta; its scopes and token lifetimes are not configurable; concurrent refreshes from one client revoke the sign-in, which the core's serialisation avoids within one process (two cores on one workshop folder are excluded by the workshop lock, DEC-056).
