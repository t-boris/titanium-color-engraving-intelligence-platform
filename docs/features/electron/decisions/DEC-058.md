## Context

DEC-028 proposed a thin HTTPS API on Vercel over one Neon database with public reading only; DEC-038 and DEC-041 then settled that the first online beta also has invitation-only private laboratories, which F-001 recorded as a contradiction with DEC-027/028's public-only wording. DEC-043 chose new Neon and Vercel projects in the owner's accounts with Neon Auth as the managed sign-in (DEC-040). REQ-086 and REQ-087 ask for anonymous public discovery, server-enforced ownership, invitation-verified private access, atomic immutable releases, idempotent retries and retrieval while the author's computer is off. The .tcelab v1 format (DEC-049) is read in constant memory by lab_format.py, which the server can run unchanged.

## Alternatives

1. A Node or Next.js API: the release validation would have to be rewritten and kept equal to the Python reader; Python Functions on Vercel run FastAPI directly.
2. Releases in object storage (Vercel Blob or S3): a second service, a second set of credentials and a second consistency boundary for files of at most 64 MiB; Postgres rows of 1 MiB chunks keep release and catalogue in one transaction.
3. The desktop talking to Postgres through Neon's Data API with RLS alone: the finalize validation, hashing and idempotency need server code, and a leaked anon key would expose the whole catalogue's write path.
4. Private access by shared secret links without sign-in: a forwarded link is unrevocable and the owner cannot see who reads.

## Decision

The cloud is the folder cloud/ of this repository: a FastAPI application deployed as the Vercel project titanium-labs-api (Python runtime, region iad1), one Neon project titanium-labs (Postgres 17, aws-us-east-1, database titanium_labs) with Neon Auth as the sign-in. The server reuses lab_format.py and the lab-v1 schema verbatim (a copy under cloud/ kept byte-equal by a test) for validation. Tables: lab (id, owner_id from Neon Auth, name, visibility public or private, created_at), release (id reserved at publication, lab_id, number, content_sha256, manifest, byte_size, record counts, terms, previous_release_id, published_at), chunk (release_id, n, bytes of at most 1 MiB), publication (the upload: id, lab_id, owner_id, idempotency_key, reserved release id and number, expected_previous_release_id, declared sha256, size and chunk count, state uploading, finalized, failed or expired, expires_at), release_withdrawal (release_id, observation ids, reason, created_at; separate from release content), invitation (lab_id, token hash, created_by, expires_at, accepted_by, revoked_at), membership (lab_id, account_id, via invitation), idempotency (account_id, key, operation, stored response). Endpoints: GET /labs, /labs/{id}, /labs/{id}/releases, /releases/{id}/manifest, /releases/{id}/chunks/{n}, /releases/{id}/withdrawals (public labs without an account; private ones for the owner and members); POST /labs; POST /labs/{id}/publications (reserve), PUT /publications/{id}/chunks/{n}, POST /publications/{id}/finalize, POST /releases/{id}/withdraw; POST /labs/{id}/invitations (a link with a one-time token), POST /invitations/{token}/accept, DELETE /labs/{id}/invitations/{iid}, DELETE /labs/{id}/members/{account_id}. Authentication is a Bearer JWT issued by Neon Auth and verified against its JWKS; the account id is its subject. Every mutation checks the owner in the API and again through row-level security: requests run as the non-privileged role app_api with the account id set per request; the owner role is used by migrations only (cloud/migrations/*.sql, applied by cloud/tools/migrate.py). Finalize streams the chunks through lab_format.read with the default resource policy, checks the content hash, the schema, the limits, that the release's lab and release ids are the reserved ones and the author is the owner, and that expected_previous_release_id is the lab's latest; then it inserts the release and the catalogue entry and marks the publication finalized in one transaction; an incomplete publication is never visible and expires. The same idempotency key returns the stored response; a wrong expected previous release answers 409. Downloads are the same 1 MiB chunks, which the desktop importer already consumes; the author's computer is not involved after finalize. The desktop keeps the access token in Electron safeStorage; sign-in happens in the system browser and returns by a loopback callback with state and PKCE (C3). Participant contributions stay outside the first online beta (REQ-086).

## Reason

One Python reader validates releases on the author's machine, the reader's machine and the server, so the three cannot disagree; one Postgres transaction makes a release and its catalogue entry appear together or not at all; Neon Auth gives sign-in, recovery and JWKS without a password table of our own; invitations with memberships give revocable private access the owner can inspect; chunks of 1 MiB stay under the Functions request limits and need no second storage service for files bounded at 64 MiB by DEC-055.

## Consequences

DEC-027 and DEC-028 are superseded where they say public reading only and where DEC-028 sketches the resources: this decision is the API contract; F-001 is closed by it. psycopg[binary] is a dependency of cloud/ only. tests/test_cloud_api.py runs the API against an in-memory repository in the main suite; tools/cloud_smoke.py runs the SQL, the policies and an end-to-end publish and connect against the deployed service and records the evidence under docs/features/electron/. Secrets (DATABASE_URL, the Neon Auth settings) live in Vercel's environment and in the owner's keychain or home folder, never in the repository.
