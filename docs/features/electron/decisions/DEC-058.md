## Context

DEC-028 proposed a thin HTTPS API on Vercel over one Neon database with public reading only; DEC-038 and DEC-041 then settled that the first online beta also has invitation-only private laboratories, which F-001 recorded as a contradiction with DEC-027/028's public-only wording. DEC-043 chose new Neon and Vercel projects in the owner's accounts with Neon Auth as the managed sign-in (DEC-040). REQ-086 and REQ-087 ask for anonymous public discovery, server-enforced ownership, invitation-verified private access, atomic immutable releases, idempotent retries and retrieval while the author's computer is off. The .tcelab v1 format (DEC-049) is read in constant memory by lab_format.py, which the server can run unchanged.

## Alternatives

1. A Node or Next.js API: the release validation would have to be rewritten and kept equal to the Python reader; Python Functions on Vercel run FastAPI directly.
2. Releases in object storage (Vercel Blob or S3): a second service, a second set of credentials and a second consistency boundary for files of at most 64 MiB; Postgres rows of 1 MiB chunks keep release and catalogue in one transaction.
3. The desktop talking to Postgres through Neon's Data API with RLS alone: the finalize validation, hashing and idempotency need server code, and a leaked anon key would expose the whole catalogue's write path.
4. Private access by shared secret links without sign-in: a forwarded link is unrevocable and the owner cannot see who reads.

## Decision

The cloud is the folder cloud/ of this repository: a FastAPI application (entry cloud/index.py, which Vercel's Python runtime recognises without configuration) deployed as the Vercel project titanium-labs-api at https://titanium-labs-api.vercel.app (region iad1), one Neon project titanium-labs (Postgres 17, aws-us-east-1, database titanium_labs) with Neon Auth (Better Auth) as the sign-in. The server reuses lab_format.py and the lab-v1 schema verbatim (copies under cloud/titanium_cloud/ kept byte-equal by tests/test_cloud_shared.py and refreshed by cloud/tools/sync_shared.py). Tables: lab (id, owner_id from Neon Auth, origin_lab_id of the author's own laboratory, name, visibility public or private, created_at), release (id reserved at publication, lab_id, number, content_sha256, manifest, byte_size, record counts, terms, previous_release_id, published_at), chunk (release_id, n, bytes of at most 1 MiB), publication (the upload: id, lab_id, owner_id, idempotency_key, the reserved release id and number, expected_previous_release_id, state uploading, finalized, failed or expired, expires_at; the file's hash, size and chunk count are declared at finalize, because the file is written with the reserved identity after the reservation), release_withdrawal (separate from release content), invitation (lab_id, token hash, created_by, expires_at, accepted_by, revoked_at), membership (lab_id, account_id), idempotency (account_id, key, operation, stored response); the handoff table of migration 0002 was dropped by migration 0003 (DEC-060). Endpoints: GET /health, /labs, /labs/{id}, /labs/{id}/releases, /releases/{id}/manifest, /releases/{id}/chunks/{n}, /releases/{id}/withdrawals (public labs without an account; private ones for the owner and members, 404 to everyone else so that their existence is not hinted); POST /labs; POST /labs/{id}/publications (reserve), PUT /publications/{id}/chunks/{n}, POST /publications/{id}/finalize, GET /publications/{id}, POST /releases/{id}/withdraw; POST and GET /labs/{id}/invitations, DELETE /labs/{id}/invitations/{iid}, POST /invitations/{token}/accept, GET /labs/{id}/members, DELETE /labs/{id}/members/{account_id}; GET /auth/config, GET /signin, GET /consent and GET /auth/return (the sign-in pages of DEC-060). Authentication is a Bearer JWT issued by Neon Auth and verified against its JWKS (RS256, ES256 or EdDSA, key by kid, cache refreshed on an unknown kid); the account id is its subject; the issuers and audiences accepted are lists (DEC-060: the desktop's OAuth access tokens and the JWT plugin's tokens of a browser session). Every mutation checks the owner in the API and again through row-level security: requests run as the non-privileged role app_api with the account id set per transaction (set_config local, since the pooled connection keeps no session state); RLS is enabled, not forced, so that the owner role used by cloud/tools/migrate.py and the live tests' clean-up can work; the API role never bypasses it. Finalize streams the chunks through lab_format.read with the default resource policy, checks the declared and the manifest's content hash against the bytes, the schema, the limits, that the lab's origin id, the release id and number are the reserved ones and the author is the owner, and that expected_previous_release_id is the lab's latest; then it inserts the release, copies the chunks and marks the publication finalized in one transaction; an incomplete publication is never visible and expires. The same idempotency key returns the stored response; two reservations against the same latest release both receive the next number and the second finalize answers 409 and must reserve again, so numbers stay sequential and nothing is overwritten. Downloads are the same 1 MiB chunks, which the desktop importer consumes; the author's computer is not involved after finalize. Sign-in: the handoff first described here (the page leaving Neon Auth's session token with the API under a one-time code) does not work against the real Neon Auth, which authenticates only its HttpOnly signed cookie; the sign-in is Neon Auth's OAuth provider with the core as a public client, authorization code with PKCE, the state carrying the core's loopback port, the cloud's /auth/return forwarding the browser to the core's callback, and a refresh token kept in the workshop folder (cloud/session.json, mode 0600, like the LAN keys), as DEC-060 records. Participant contributions stay outside the first online beta (REQ-086).

## Reason

One Python reader validates releases on the author's machine, the reader's machine and the server, so the three cannot disagree; one Postgres transaction makes a release and its catalogue entry appear together or not at all; Neon Auth gives sign-in, recovery and JWKS without a password table of our own; invitations with memberships give revocable private access the owner can inspect; chunks of 1 MiB stay under the Functions request limits and need no second storage service for files bounded at 64 MiB by DEC-055.

## Consequences

DEC-027 and DEC-028 are superseded where they say public reading only and where DEC-028 sketches the resources: this decision is the API contract; F-001 is closed by it. psycopg[binary] is a dependency of cloud/ only. tests/test_cloud_api.py runs the API against an in-memory repository in the main suite; tools/cloud_smoke.py runs the SQL, the policies and an end-to-end publish and connect against the deployed service and records the evidence under docs/features/electron/. Secrets (DATABASE_URL, the Neon Auth settings) live in Vercel's environment and in the owner's keychain or home folder, never in the repository.
