## Context

Prototype v10 is in Russian and its SPEC.md keeps user-facing names and messages in Russian. The server raises its error messages in English. REQ-011 describes browser screens without fixing a language.

## Alternatives

1. English UI.
2. Russian screens with English server messages as a known gap.
3. Both languages, switchable.

## Decision

All screens, labels, states and notifications in the browser UI are in Russian. The server keeps English messages and returns them in the `error` field of its responses together with a stable `kind`. The UI translates the messages it recognises through one translation table; a server message with no entry is shown unchanged with the note that it comes from the server, never hidden. The API field names, the log output and the documentation stay in English.

## Reason

The user chose this option. It matches the approved prototype and the language of the operator.

## Consequences

Any new server message needs an entry in the UI's translation table to appear in Russian. An unmatched message appears in English with a marker, which is a visible gap rather than a silent one. Switchable languages are out of scope because no requirement asks for them.
