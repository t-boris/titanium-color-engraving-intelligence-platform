## Context

Operator, 2026-10-20: «Мне нужно реализовать работу над ошибками. Я хочу, чтобы результат, который я вижу, соответствовал результату, который выгравирован. После каждого лайтберна я буду делать отчёт, и он должен сделать вывод насчёт существующих работ… или в самой работе записать результат. Он должен проанализировать, подменить какие-то цвета, изменить параметры, найти в чем проблемы.» Checked in code and real data: a work's palette is re-read on every view, so a new measurement already changes the preview; but a vector work stores the colour its preview showed (layer lab) with prediction None, so the pair report shows no planned-vs-measured for it; an export keeps only its number of layers; and the engraved file need not be the exported one (pair 77 'Inna + Boris 2' matches 0 of its 16 layers with the layers of work 22 by settings).

## Alternatives

1. A separate screen of all works and conclusions (the operator chose the conclusion inside the work plus a mark in the list)
2. Apply replacements automatically (the operator chose to apply them themselves)
3. Match layers by index (breaks when the engraved file is edited or renumbered: 0 of 16 matched for pair 77)
4. Measure drift against the colours last stored at any edit (an edit of one layer would clear the marks of the others)
5. Per-region measurement on the aligned photo (not in this release; layers are measured as a whole)

## Decision

1) Each export keeps what every layer promised (settings, colour and basis, area, regions). 2) The photograph of an engraving (an accepted pair linked to the work) is set against that promise, matching layers by their settings (0.5 % tolerance), never by layer number; the review (per layer: promised and measured colour, ΔE, shifts of lightness, chroma and hue, what the measurements themselves say, a general shift when most layers moved one way) is stored in the work, one per engraving, and shown on the work's Result tab with the work drawn in the promised and in the measured colours. 3) After every acceptance, re-measurement or deletion the layers of every work of that laser and lens whose recipe colour moved from the last file's promise are counted and kept in the work for the list of works; the work's own screen computes it live. 4) For each source colour of a moved layer the closest measured colour is proposed when it is clearly nearer; the operator applies it as an ordinary undoable edit; the system never changes a colouring or an engraved file itself. 5) A file made before promises were kept is reconstructed from the work's layers while its colouring is unchanged, and marked approximate. Assumptions, not measurements: a difference is 'visible' from 5 ΔE (raised to the photograph's own chart residual when larger; the chart's honest error is about 3.6), a replacement must come 1 ΔE nearer, a chart residual above 7 makes the photograph doubtful, a lightness shift of 3 on 75 % of layers is called systematic.

## Reason

The operator wants what is seen to equal what is engraved and the conclusion kept where they work. Matching by settings is the only key that survives LightBurn edits and renumbering. Proposing and applying by the operator keeps already engraved files and the operator's colour choices untouched (the operator chose «предлагать, применяю я»). The promise is the baseline of the drift because a baseline that moves with every edit would silently clear the marks of layers the operator has not dealt with.

## Consequences

New module work_review (pure) and work_errors (database); plan data gains exports[].promised, reviews, attention; the list of works gains attention and review; the pair report gains work_review; GET /api/vector/{id}/engraved.png draws the promised or measured colours. Nothing is added to a work that was never exported. Per-region colours, causes beyond what the measurements say, and parameter changes are not in this release: a moved colour is replaced by another measured colour, not by new settings.
