## Context

A photo zone (REQ-073) asks for the same scale many times in one screen: its picture, its «Вид» tiles (ten kinds, ten requests), the list of scales, the dots' power. prediction_store.collect read every observation and parsed every accepted check's JSON on each call: 0.06 s a call, 5-11 calls a request; tiles took 0.3 s each, the kinds 0.75 s, the list of scales 1.6 s on the live data.

## Alternatives

1. A cache keyed by the newest pair id or accepted_at: misses a check re-measured in place (data_json updated) - wrong colours until a restart
2. One request drawing every tile: one slow request (2 s or more) instead of ten fast ones
3. Per-table change counters: SQLite has none; triggers on every table would change the schema for a cache

## Decision

Store.stamp() gives the state of the data as (rows written through the store's connection, PRAGMA data_version: commits by any other connection to the file). collect is memoised per (store, mode, stamp), up to 64 modes; each caller gets lists of its own, the points are frozen. photographed_kinds (also per stamp) lists the kinds any accepted check measured a tonal profile of, so a zone does not look for tones of kinds never photographed. A zone picture's cache key holds only the settings its kind draws from.

## Reason

The stamp changes with every write, ours or another program's, so a memoised result can never be stale; reads cost nothing. Every editor action writes the work, so the memo helps within a request and across the tiles of one state, which is where the repeats are. Measured on a copy of work 22: tile 0.05 s, kinds 0.08 s warm and 0.15-0.25 s after a change, list of scales 0.75 s first and 0.05 s after.

## Consequences

The photo works and the grey-scale pages also reuse collect's results while nothing is written. A write anywhere (an editor action included) clears the reuse: the first request after it reads the measurements again (0.06 s per mode).
