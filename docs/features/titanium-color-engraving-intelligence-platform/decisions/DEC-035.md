## Context

The user supplied the documentation of their JPT YDFLP-E-60-M7-M-R laser and wants it reused later, with descriptions and automatically drawn charts for each laser. REQ-010 keeps pulse width, line interval and passes as profile constants and makes a new version for every change. The documentation holds much more (cut-off table, test results, controller settings, photographs) that does not belong in a version-controlled constant set.

## Alternatives

1. Put the passport data into the laser profile constants (every correction of a note would create a new profile version).
2. Keep the passport as free text in the profile name or in a setting (no charts, no validation, no reuse across profiles).

## Decision

A device is a separate table with a JSON passport and a document list. A laser profile version has an optional device_id. Editing the device or the link is done in place and never creates a profile version; the profile constants stay the only constants stored with measurements. A pulse width that is not a selectable step of the linked device is refused.

## Reason

The same laser serves several profiles and several pulse widths; the passport can be completed later without touching measured data. Refusing non-selectable pulse widths protects the data: the laser ignores an undefined value and keeps the last valid one, so such measurements would not mean what the profile says.

## Consequences

The database gets two tables and one nullable column added by an idempotent migration; an older installed version keeps working on the same data directory. Plates created before a device was linked have no operating-point figures.
