## Context

The recipe key of an observation includes every preserved LightBurn setting that is not one of the six numeric ones. That includes the layer's priority (its place in the run order), so the same recipe in two files with different priority numbers never groups, and repetitions are never counted for validation. Changing the key of rows that already exist would orphan stage and event history of the knowledge table.

## Alternatives

1. Keep priority in the key
2. Re-key all existing observations and migrate knowledge rows
3. Also drop tab settings

## Decision

New observations store their layer settings without the run-order tag (priority); all other settings, including nested sub-layers, stay in the key. Existing observations are left as they are and their keys are unchanged (checked against the previous algorithm); only data accepted from now on groups across files. Tab settings stay in the key because they decide whether a cut piece is held.

## Reason

Execution order matters only through overlaps inside one job, which the overlap rule handles; it says nothing about how a layer engraves. Excluding it lets the same recipe repeat across works, which is what validation counts.

## Consequences

Old and new observations of one recipe do not merge until a migration is decided; this is the only open point and needs the operator's confirmation. The original file and the layer report still carry the priority.
