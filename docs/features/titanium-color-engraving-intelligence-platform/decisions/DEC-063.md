## Context

DEC-042 (answer B to Q-022) removes operator-managed laser profiles. On 2026-10-18 a laser_profile row was still a NOT NULL foreign key of plate, plan, pair, observation, knowledge, target_color and proposal, the only route to the laser and lens of a record, the key of the rules setting, and a required choice before ingest, artwork, photo engraving, the designer and the operating-point calculator. The operator was offered a hidden internal identity row or a full migration and chose the full migration.

## Alternatives

1. Keep laser_profile as a hidden internal identity row per laser and lens, never shown to the operator (smaller change, the profile stays in the data model)

## Decision

Each of the seven tables is rebuilt by an idempotent migration so that it carries device_id (the physical laser) and lens_id (the lens record installed when the work was engraved; NULL means unknown) instead of profile_id. The old profile id is kept only as legacy_profile_id for provenance, and the laser_profile table stays as a read-only archive that no screen, route or calculation uses. Comparable knowledge, rules, target colours and proposals are partitioned by the setup key of device and lens (an unknown lens is its own partition, never equal to a known one); within a partition the recipe key (all job settings, DEC-051) separates pulse width, line interval and passes. Measured values of observations are copied unchanged and the immutability triggers are recreated; the migration runs inside one transaction, only after a backup of the database file, and refuses to run on a database it cannot map. Every form chooses a laser and, where it matters, a lens; nothing asks for a profile. A lens is identified by its record; its later edits do not split knowledge, the snapshot on plates and plans keeps the configuration used.

## Reason

The operator chose it: the profile disappears from the data model, not only from the screens, so no future code can group or gate by it again.

## Consequences

Version 0.4.0 changes the database schema; an older installed version cannot open a migrated data directory, so the deploy keeps a backup and the migration is tested on a copy of the operator's live database. Supersedes the hidden-profile approach of capability plates. Rules saved per profile move to the partition of that profile's laser and lens.
